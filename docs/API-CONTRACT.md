This is the handoff document for the backend. The Next.js frontend is finished
and self-contained: it currently renders a snapshot of the existing site. When a
backend implements the endpoints below, the frontend switches to it by setting
two environment variables — no code change.

## Ground rules

1. **The response shapes are fixed.** They were captured from the live site, and
   the frontend validates every response against the JSON Schemas in
   `docs/api-contract/`. A response that does not match fails loudly rather than
   rendering wrong content.
2. **Text is never normalised.** Typos, mixed Bangla/English and the known
   content mistakes listed in `docs/01-SITE-AUDIT.md §9` are real data. Fix them
   in the admin panel, not in the API.
3. **Links are verbatim.** `href` may be `"#"` or `null`; that is meaningful —
   it is what the current site does, and the frontend reproduces it exactly.
4. **Every current URL must still work.** The frontend routes `/`, `/about-us`,
   `/{package-slug}` (e.g. `/gold-ownership-2`), `/offer`, `/book-now`, `/event`,
   `/events/{slug}`, `/blogs`, `/blog-details/{slug}`, `/gallery` and `/contact`.
   Slugs come from the API, so they must match the existing ones.
5. **Media** may be absolute URLs or paths. Paths are resolved against
   `MEDIA_BASE_URL`. The current media is mirrored in
   `services/frontend/public/media/` with its original relative paths — that plus
   `services/frontend/src/fixtures/*.json` is the data to seed the database with.

### `GET /events/filter` query parameters

| Parameter | Value |
|---|---|
| `start_date` | `d-m-Y`, e.g. `29-09-2026`. Optional. |
| `end_date` | `d-m-Y`. Optional. |
| `category_id` | Category id from `/events`. Empty means all. |

Behaviour to preserve from the current site:

- Dates are **`d-m-Y`** (day-month-year, zero padded) — the format the existing
  date picker sends. Not ISO.
- If exactly one of `start_date`/`end_date` is given **and** `category_id` is
  empty, the filter is ignored and the full list is returned.
- An event with no dates never matches a date filter.
- An empty result is a `200` with an empty array, not a `404`.

## `POST /forms/contact`

Request body (`application/json`). Field names are exactly those the current
site submits:

| Field | Type | Notes |
|---|---|---|
| `name` | string | Required by the modal form, not by the contact page form. |
| `phone` | string | Same. The page form uses a numeric input. |
| `email` | string | Same. |
| `address` | string | The modal sends the literal string `"N/A"`; the page form sends the typed address. |
| `message` | string | Optional in both. |

Responses:

- `200` — accepted. The frontend then shows the site's existing success text,
  "✓ Message sent successfully!".
- `422` — validation failed, with field-level messages the frontend maps back
  onto the inputs:

```json
{
  "errors": {
    "email": ["Enter a valid email address."],
    "phone": ["This field is required."]
  }
}
```

- Any other status is reported to the visitor as a generic failure.

> There is **no comment endpoint**. The "Leave a Reply" block on event pages is
> decorative markup on the current site — no form, no handler, nothing stored —
> so the frontend does not render it. If comments are wanted, that is new scope.
